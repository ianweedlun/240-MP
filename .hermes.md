# 240-MP Project Rules

This repository is public. Never commit hostnames, account names, cron IDs, ticket numbers, commit hashes, key paths, or infrastructure addresses. Local operational detail lives in the ai-memory note `ops/240mp-deploy-and-ci.md`; cross-project engineering defaults live in the ai-memory profile page `workflow/engineering-gains.md`.

## Session start (contract)
First action, one parallel batch: remote heads (`git ls-remote`), CI conclusions (`.conclusion`, never run status), deploy truth (two-state check below), open issues (maintainer replies are required input — fold and acknowledge).
Load the `240-mp-development` skill; its references load on demand: `debug-telemetry.md`, `comms-attribution.md`.
No planning dumps or re-derivation arcs: go straight to the accelerator chain. Stack design clarifications at session start; "go" means implement.

### External contracts
Read the authoritative contract before designing against an interface — an API's OpenAPI spec **and** its prose docs, another project's source constants, an on-disk marker layout. Save it under `docs/api/` and name it in the card. **Probes verify a contract; they never discover one.** Where spec and prose disagree, record both and settle with a live probe.
Never invent an identifier: endpoint path, enum value, marker filename, client constant. Enumerate it.
Parse the full documented response. Every discarded field is a design decision needing a stated reason, not a simplification; persist new fields too, or the round-trip drops them at a second boundary.
Verify a trigger's actual precondition, not its name.
A gate is the real consumer doing its job, and it must fail on known-bad input. A gate with no negative case proves nothing. Confirm the new test actually compiled and ran before trusting green.

### Accelerators
1. Offscreen local loop first: `QT_QPA_PLATFORM=offscreen` plus the key channel and state log — seconds per navigation bug, zero CI and no reboot.
2. Prior art beats re-diagnosis: `git log -S <symbol>` across branches; diff against the last working version before touching code.
3. Live-probe hypotheses on the target directly — argument-list probes beat reading code paths.
4. Unit tests are cheap and wired: `cmake -B build-test -DBUILD_TESTS=ON && ctest` on every logic change.
5. Deploy truth = two states, never one marker. OFFICIAL: installed binary md5 equals the CI artifact md5 named by the last-deployed marker, and no RC markers exist. RC: RC revision set, restore revision non-empty, last-deployed revision still naming the official restore target, and the RC md5 marker equals the archived RC tarball md5. An older RC without an md5 marker is UNVERIFIED, not drift. Anything else is drift. The check answers the OFFICIAL question only; under a live RC there is no official deployment to verify. Never trust an Actions head SHA or an optimistic marker. Exact marker names and artifact conventions are in the local ops note.
6. Deploys: one branch at a time; last push wins. Never push a branch whose head lacks a live-verified fix while the owner tests.
7. Doc-only pushes build nothing; batch code pushes so each deploy carries maximum value.
8. The skill index is compact; large knowledge blocks load on demand from its references. Name the reference in a question instead of expanding everything.
9. Harness string and script logic directly against the patched file with live-probed values. Six cheap cases beat a rebuild. Use one script on the target for navigation walks, with scoped selection feedback.

## Daily burst workflow (owner ruling 2026-11-28)

Goal: agent-owned visual validation, short bursts, one promotion per day, owner never in the loop.

1. **Burst** (30-45 min, one behavior, one worktree): local offscreen repro, two-sided test, ctest. Hard stop at 45 min with a handoff comment even if unfinished.
2. **Mirror gate** after every burst: qualified x86 mirror — same source SHA, Qt 6.8.2, same font/config fixture, fixed geometry. Run `QT_QPA_PLATFORM=xcb` on Xvfb with software GL and capture the FULL root window with `ffmpeg -f x11grab`, so the app, mpv, and RetroArch are all in frame. PIL for exact counts, vision for semantics, state log + journal for truth. Qualify the mirror with a golden suite on both hosts before trusting it.
3. **Pi gate** once daily before promotion: current Pi only, no second board. Reserved RC window with saved restore rev and two-state + md5. Bundle app screenshot + mpv IPC `screenshot-to-file` + RetroArch F8 screenshot; never claim game or video pixels from the app screenshot alone. The first Pi gate consumes the stale `pr-166` RC markers via restore.
4. **Batch and promote**: at most one dev-to-beta promotion per day after all gates; agent self-merges; changelog and issue closed. Owner review comments are advisory, never a gate.
5. **Churn controls**: CRT wheel fires only after CI concludes success for the same SHA; CI-failure issues dedupe and auto-close on later green; RC stays validation only, never official.

## Definition of done (per named behavior)
1. Implemented on a dev-forked branch with conventional commits.
2. Pure logic covered by unit tests, green.
3. CI green for the branch tip (arm64 and macOS; macOS never blocks the target build).
4. Deployed through the runner pipeline and verified by the two-state plus md5 gate with service active. An overnight RC is validation, not done.
5. Every user-visible behavior proven by the agent CRT-validation wheel. Compiling or "works locally" is not done.
Owner CRT proof no longer sits in a human's hands. The agent drives the wheel (see .github/workflows/pi-crt.yml + scripts/crt-validate.sh): replayable named cases with exact key sequences and visual invariants, driven through the debug key channel, captured side-by-side with state-log ground truth, and judged by vision on app-initiated screenshots. Evidence is posted on the issue when a case closes.
Owner CRT judgment survives only for cases where no invariant can be encoded: a one-line review comment on the issue. It is not a gate, and it doesn't block closing the card.
6. Changelog entry and tracking issue closed.
Code without CRT-validation evidence is "implemented, unvalidated" — never call it done. Ordinary cards open no promotion PR for it; overnight cards may open the narrow RC PR but never merge it or claim validation from it.

## Agent CRT validation (the wheel removes the owner)
- DoD item 5 is served by the agent CRT-validation wheel, not by the owner at the CRT.
- Named cases live in `docs/crt-validation-cases.md`. Each case is a replayable card: exact key sequence(s), expected visual invariants (read as machine-checked evidence, never "looks right"), and a required evidence bundle (screenshot, state-log tail, vision verdict).
- The wheel is driven through the debug key channel (`POST /key` on :8081, or the `240mp_key.in` FIFO), one tap per line — no mouse, no view that needs the owner. `bash scripts/crt-validate.sh <case>` drives the case and prints PASS/FAIL plus the evidence files.
- Vision runs last, on app-initiated screenshot filenames the view tags (see Debug stack), to land a per-case verdict. The state log is ground truth for nav depth, key delivered/suppressed, and row selection — it is read by the agent, not the owner.
- Owner CRT judgment (invariants that can't be encoded) is recorded as a review comment and excluded from the "done" gate; doX items that only an owner can mind stay open on the issue as a review task, not a close blocker.
- The wheel is idempotent and safe: it only taps navigation/playback keys, never writes config, and restores the Pi to the deployed revision.

## Navigation and input
- `appNavStack` holds `{source, params, listState}`; module views declare `navigateTo` and `goBack`, bridged by Main.qml. Views get focus and force active focus on load.
- ModuleList: enabled modules from `scan_for_modules()`; Up/Down wraps; Return opens the entry; Escape goes to Settings.
- Settings: flat model of headers and rows; Left/Right cycles and auto-saves; Return opens a submenu; Escape goes back.
- RemapControls: eight rows; Return captures a key, Escape cancels, duplicates are cleared, result saved to the remote keymap.
- Input paths: gamepad through SDL, keyboard through the event filter, consumer control through evdev, media keys through the player IPC. All synthesized presses pass through one delivery chokepoint.
- Gameplay suppression: while the emulation child runs or the display handoff owner is that child, synthesized presses are dropped so a quit key does not also pop the app nav stack.
- Channel zapping: dedicated evdev codes and remap actions map to channel keys handled by the channels module.
- Synthesized events carry a distinctive scan code; remaps are additive and never remove defaults.

## Virtual channels module
Manifest-driven, default off, registered like any module. Dial channels are numbered with rolling schedules sourced from local media, media-server backends, and the weather channel when enabled. Built-in numbers never collide; tests cover weather on.
The channel banner OSD is a script message gated on the Lua script existing; the script is added to player startup arguments only when found.
Naming: this fork uses `auto_fit` and `autoFitEnabled`; `autoCropEnabled` does not exist — never reintroduce it.
Guide previews are bounded; surfacing away must cancel the preview. Channel presses are logged through the common input chokepoint.
Views follow the one-component-per-file pattern used by the larger modules; do not fold them together.

## Debug stack
Telemetry is debug-only and compiled out of release builds. Ladder, cheapest first:
1. State log: timestamped events for loads, navigations, internal back and forward, key delivered or suppressed, and row selection including the initial selection. Stack skew and key leaks are directly visible there.
2. Debug key channel: lines written to a FIFO are injected through the same delivery chokepoint on a short poll. With offscreen Qt this drives full navigation loops in seconds. No rendering, so layout and highlight visuals still need the target.
3. Screenshot filename view-tag names the open view; use it before vision.
4. Process list and journal lines are the truth for child-owned display: the app renderer is suspended then, so screenshots are stale.
5. Vision analysis last, only for visual truth or when asked.
Screenshots are app-initiated and portable across Qt platforms. During a launched game the renderer is suspended, so a capture is stale — use the process list and journal instead. Remote capture uses the one injectable key; the physical function key also works. Tap keys, never hold.

## Validation workflow
Push to dev or a feature branch builds it; promotion is agent-gated after local-first, CI, deploy-truth, and CRT-wheel gates. An RC PR deploys its own head as validation only and auto-restores on close. Offscreen lab drives logic; target journal and state-log tails are read-only diagnosis. Reproduce logic bugs locally first. Screenshot capture is for layout checks only. The agent runs the CRT-validation wheel (case card + key sequence + screenshot + state-log tail + vision verdict) and posts evidence on the issue. Owner CRT proof is no longer required to close a card; the owner's remaining role is a review comment on invariant-free cases.
Always ask when blocked. Trust but verify — validate with the available signals, not descriptions.
Target: Raspberry Pi 4B+ with composite CRT. GitHub: use the fork and its issues for tracking. Build: CI cross-compiles the tarball; local lab builds run on the Debian host.
