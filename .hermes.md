### Definition of done (per named behavior)

1. Implemented on a dev-forked feature branch with conventional commits.
2. Pure logic (mappings, bands, parsers) covered by unit tests, run green.
3. CI green (arm64 + macOS) for the branch tip.
4. Deployed to the Pi through the runner pipeline (beta push = Ian's merged PR, never an agent direct push); md5 gate + service-active verified.
5. Every USER-VISIBLE behavior in the request proven by owner CRT testing (Ian drives
   the console and reports what he sees — his word is the artifact). Agent-side Pi
   screenshot capture happens ONLY when Ian asks for it. Compiling is not done;
   "works on my machine" is not done.
6. Changelog entry + tracking issue closed.
A feature whose code exists but whose behaviors lack owner CRT proof is at stage
"implemented, unvalidated" — never call it done, and never open the dev→beta PR for it.

## Navigation System (Main.qml)
- `appNavStack: []` — array of `{source, params, listState}` pushed on `navigateTo`, popped on `goBack`
- `appCurrentParams` — current params dict passed to active view
- ModuleLoader loads `views/ModuleList.qml` by default
- Module views declare `signal navigateTo(path, params, listState)` and `signal goBack()`
- Main.qml bridges these via Connections
- Module views get `focus: true` + `forceActiveFocus()` on load

### ModuleList.qml (main menu)
- ListView of enabled modules from `appCore.scan_for_modules()`
- Row: `{name, entry_point, params?}` — params from backend `get_menu_entries()`
- Up/Down: cycle with wraparound
- Return: `navigateTo(row.entry_point, row.params, {currentIndex})`
- Escape/Backspace/Back → `Settings.qml`

### Settings.qml
- Flat model: section headers + selectable rows
- `list_single`: Left/Right cycles options, auto-saves
- `submenu`: Return opens ModuleSettings/Update/RemapControls
- Escape/Backspace/Back → `goBack()`

### RemapControls.qml
- 6 rows (Up/Down/Left/Right/Select/Back) showing current remap
- Return on row → capture mode (`capturing=true`)
- Capture overlay swallows all input, reports via `auxButtonPressed`
- Escape during capture → cancel
- On finish: clears duplicates, saves to `config.json` → `app.remote_keymap.<action>`

## Input Flow
1. **Gamepad** → SDL poll (16ms) → `handleButton/handleAxis` → `pressAction/releaseAction`
2. **Keyboard** → `eventFilter` → `deliverPress` (same synthesized path)
3. **Consumer Control** (evdev) → `onConsumerControlReadable` → `beginPress/releaseAction`
4. **Media keys** → `mpvKeyRequested` → mpvController.sendKey (bypasses QML)
5. **Gameplay suppression**: while `RetroArchBackend::gameRunning()` is true (live launchGame
   child) or DisplayHandoff owner is `retroarch`, `deliverPress` drops the key — the child
   already read the same evdev/SDL stream; prevents a ROM-quit Back from also popping the QML
   nav stack (user-visible: exit-after-game landed on Settings instead of ModuleList).

### Key Mapping
| Action | Qt Key | evdev |
|--------|--------|-------|
| Up | 103 (Up) | KEY_UP=103 |
| Down | 108 (Down) | KEY_DOWN=108 |
| Left | 105 (Left) | KEY_LEFT=105 |
| Right | 106 (Right) | KEY_RIGHT=106 |
| Select | 28 (Return) | KEY_ENTER=28 |
| Back | 1 (Escape) | KEY_ESC=1 |
| PlayPause | 57 (Space) | KEY_SPACE=57 |

- Synthesized events carry `nativeScanCode=0x240F00D` for eventFilter distinction
- Remapped keys: `config.json` → `app.remote_keymap.<action>` → `m_keyRemap[qtKey] = action` (additive)

### Per-View Key Behaviors
- **ModuleList**: Escape→Settings, Return→entry_point, Up/Down→nav
- **Settings**: Escape→goBack, Return→submenu/quit, Left/Right→cycle
- **Module views**: Escape→goBack, Return→select, Up/Down→nav
- **Player views**: Escape→goBack, Return→play/pause, Up/Down→seek, Left/Right→fine seek
- **RemapControls**: Return→start capture, Escape→cancel

### Key Remap (InputManager.cpp)
- `m_keyRemap[qtKey] = action` — additive, never removes defaults
- Capture mode: `m_remapCapture=true` → eventFilter emits `auxButtonPressed(key)` instead of delivering
- Right Shift → Back (when no text field focused)
- Media keys → mpv IPC (volume, play/pause, etc.)

## Debug Stack (240mp-debug.service)
### Services started:
1. **Control server** (`control_input.py`): POST `/key` on **:8081**, uses `evemu-event` on `/dev/input/event0`
2. **Viewer** (Python HTTP): serves `viewer.html` on **:8082**

### Screenshot Capture (App-initiated)
- 240-MP runs on EGLFS (DRM/KMS), not Linux framebuffer
- App-initiated screenshots via `AppCore::captureScreenshot()` / `AppCore::takeScreenshot()`
- Saves to `/tmp/240mp_screenshot_<view-tag>_YYYYMMDD_hhmmss.png` — `<view-tag>` is the open
  view (`module-View`, e.g. `retroarch-Games`, `ModuleList`), tagged via Main.qml's
  `ModuleLoader.onLoaded → appCore.note_view()`. Read the view from the filename; no need to
  ask vision "which screen is this".
- **During a launched game the app's renderer is suspended** (the child owns the display):
  an F12 capture is black/stale and the view tag may not reflect live navigation. Do **not**
  use screenshots to know if a game is running — use `pgrep -a retroarch` on the Pi, or the
  journal's `[RetroArch] launching` / `exited with code` lines. Screenshots are for app views
  only, taken when no child owns the console.
- Portable across all Qt platforms (EGLFS, X11, Wayland)
- Trigger via:
  - Q_INVOKABLE from QML hotkey: `appCore.takeScreenshot()`
  - Control server: map a key combo to screenshot signal (F12)
  - Direct call: `AppCore::captureScreenshot("/tmp/path.png")`

### Debug Telemetry Hierarchy (cheap → expensive — always use the highest tier that can answer)
ALL telemetry below is debug-only: cmake `TELEMETRY=OFF` (default ON in dev) compiles away every
C++ body (`#ifdef APP_TELEMETRY`) and makes QML telemetry no-ops (`appCore.telemetryEnabled()`
kill-switch + `note_state` stubs). Release builds are silent. Never ship these signals.

1. **State log** `/tmp/240mp_state.log` — fastest, most precise: `ssh tail`. Line format
   `<epoch-secs> <event> <detail>`. Events, by producer:
   - `load <view> stack=<n>` — view opened (Main.qml; ModuleLoader)
   - `navigate to=… stack=<n> listState=…`, `back restore=… stack=<n>` — app-level nav stack (Main.qml)
   - `nav-internal to=…`/`back=… stack=<n>` — module-internal stack (module Root machine)
   - `key <action> delivered|suppressed=game|suppressed=handoff` — InputManager::deliverPress,
     the single input chokepoint; ground truth for key-leak / stack-skew bugs
   - `select <row-name> idx=<n>` — emitted by the CORE `RowTrackingListView` primitive
     (views use it instead of bare ListView; it also fires for the INITIAL selection —
     the highlighted row is known before the first Return)
   Stack-skew bugs (exit landing in the wrong view) are DIRECTLY visible: compare stack
   depths across load/navigate/back lines; `key ... suppressed=` proves a dropped key.
2. **Debug key channel** `/tmp/240mp_key.in` — lines `up/down/left/right/select|enter/back|escape/playpause`
   are injected through `deliverPress` (200 ms poll). With `QT_QPA_PLATFORM=offscreen ./build/240mp`
   an agent drives FULL local nav loops in seconds — `pi-nav.sh local down select back` tails the
   state log after. No CI/deploy/reboot; use for QML-load errors, nav logic, stack bugs.
   No rendering: layout and row-highlight VISUALS still need the Pi.
3. **Screenshot filename view-tag** — `240mp_screenshot_<view-tag>_…png` (e.g. `retroarch-Games`)
   names the open view for free. "Which screen is this?" never needs vision.
4. **`pgrep -a retroarch` + journal `[RetroArch]` lines (Pi)** — game-running truth: during a live
   game the app renderer is suspended (child owns display); screenshots/logs reflect the app view
   that will RESUME, not the child's screen.
5. **Vision model on a screenshot — LAST RESORT.** Only when visual identification is a must
   (layout/color/display bugs) or when the user asks for a visual check. Screenshots stay
   artifacts regardless; only their VISION analysis is gated.

### Remote Navigation Loop (F12 Screenshot Workflow)
For hands-free remote debugging when user can see CRT:
1. **POST** to `http://execubot.weedlun.me:8081/key` with `{"key": "Up", "press": true}`
2. **Wait** ~200ms for UI to settle
3. **POST** `{"key": "Tab", "press": true}` → triggers `AppCore::takeScreenshot()` (injected F-series codes are dropped by Qt's EGLFS keymap; Tab is the only injectable capture key — physical F12 on the console works too)
4. **SCP** `/tmp/240mp_screenshot_*.png` from Pi to local — the filename's `<view-tag>`
   already says which view was captured; trust it and use vision only for layout/content checks
5. **Tail `/tmp/240mp_state.log`** after each key — the load/navigate/back/key/select lines
   ARE the UI state; **analyze with vision ONLY if a visual truth is needed** (layout, colors)
6. **Repeat** for next navigation step
